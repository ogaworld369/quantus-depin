## 1. 全体構造

参加デバイスは一定間隔で「チェックポイント」を作り続け、期間分をまとめて署名し、「証明バンドル（JSON）」として書き出す。バンドルは GitHub へ提出され、検証者は署名・連鎖・逐次計算を再計算して真偽を判定し、集計器（§8）が重み付けと失格判定を行う。常時稼働のサーバは使わない。チャレンジの代わりに「最新のブロックハッシュ」を各チェックポイントへ束縛する（予測不能性はチェーン自身が供給する）。

**参加手順は最小であること（設計原則）**: 参加者の操作は「アプリを入れる → ノードを開始する → 参加をオンにする」だけであり、参加の入口に条件（紹介制、アカウントの年季、預け金、本人確認など）は置かない。偽装対策の複雑さは全て集計側（裏側）の処理で引き受け、参加者に追加の操作・手続きを求めない。参入の壁が面倒だとユーザーは増えない、という判断に基づく（2026-11-07 本人指示）。

## 2. ID鍵（デバイス署名鍵）

- 方式: **Ed25519**（RFC 8032）。秘密種（seed）32バイトから鍵ペアを導出する。
- 選択理由:
  1. 決定的署名（署名時の乱数不良で秘密鍵が漏れる事故が起きない）
  2. 純Pythonの参照実装（RFC 8032 系）で外部依存なしに実装・検証でき、RFCのテストベクタで正しさを固定できる
  3. 鍵長・署名長が小さく、オフチェーンの本人性（同一デバイス性）と改ざん検知という本フォーマットの役割には十分である
- **前提の訂正（v0.3）**: v0.2 までは根拠の一つに「QuantusノードのネットワークID（libp2p ピアID）が Ed25519 系であり、同じ土俵で扱える」と書いていたが、これは誤りだった。**Quantus のネットワークID（libp2p ピアID）は Dilithium 鍵由来**であることが、実コードと実ノード実測で確認された（2026-11-07、Android連携の設計調査）。したがって本フォーマットの Ed25519 は「ピアIDと同系だから」ではなく、**オフチェーンの本人性・改ざん検知のための独立した選択**である。将来「ノード本人（ピアIDの持ち主）」と「DePIN参加デバイス」を結びつける場合は、ピアID側の鍵による別途の署名・証明が要る（本フォーマットの署名だけでは結びつかない）。
- デバイスID: `qdp1-` + SHA-256(公開鍵) 先頭12バイトの hex（24文字）。公開鍵から機械的に導出し、検証時に一致を必須とする。
- 鍵の保管（試作）: seed を JSON ファイルに保存し、ファイル権限 0600 を必須とする。**鍵読込時にも権限を検査し、グループ／他者に読めるファイルは拒否する**（v0.3、L1）。秘密の実値をログ・メモ・提出物に出してはならない。提出するバンドルには公開鍵のみが入る。
- 弱い鍵の拒否（v0.3、H6）: 検証側は、恒等点および小位数点（位数 1/2/4/8）の公開鍵・署名内 R を受理しない。これらを認めると秘密鍵なしで検証を通る署名を偽造できる。また x=0 のとき符号ビットが 1 の非正規な符号化（いわゆる negative zero）は復号時点で拒否する。
- **正直な留保**:
  - Ed25519 は古典的署名であり**耐量子ではない**。ただし本署名の役割はオフチェーン試作における「同一デバイス性」と「改ざん検知」であり、チェーン自体の耐量子性（QPoW／アカウント署名）とは別レイヤーである。将来オンチェーン連携する場合は、耐量子署名への置き換えまたはノード側鍵との併用が必要。
  - 参照実装の純Python Ed25519 は**定数時間ではなく、サイドチャネル耐性がない**。試作専用であり、本番の秘密鍵運用には使わない（§7、M4）。
  - Android Keystore のハードウェア-backed鍵は主に ECDSA P-256 で、Ed25519 のハードウェア保管は端末依存で保証されない。Android 連携では「Keystore の鍵で Ed25519 seed を暗号化して保管する」方式を既定とする（連携設計メモ参照）。本試作はソフトウェア鍵のみ。

## 3. チェックポイント

固定スロット間隔（§4 のパラメータ表で定義する `checkpoint_interval_sec`、現行 600 秒）ごとに1件作る。**間隔は参加者が選べない**（v0.3、C1）。チェックポイントの属する**スロット番号**は `slot = timestamp_unix // checkpoint_interval_sec` で定まる（v0.4 で明記。連鎖の種への束縛 §4 と、集計での重複排除 §8 に使う）。各チェックポイントの項目:

| 項目 | 型 | 内容 |
|---|---|---|
| `seq` | int | 0 始まりの連番。欠落・重複・並び替えを検知する |
| `timestamp_unix` | int | デバイス時刻（秒）。単調増加を必須とする。ただし真実性は自己申告の域を出ない（§7） |
| `best_block_number` | int | 観測した best ブロック番号。非減少を必須とする（留保は§7） |
| `best_block_hash` | hex(32B) | 観測した best ブロックのハッシュ。これが予測不能チャレンジを兼ねる |
| `observed_peers` | int | 観測ピア数（表示・異常検知用の自称値。**スコアには一切使わない**、§8.1） |
| `iterations` | int | この区間の逐次連鎖に適用した反復回数 N（§4）。v0.3 以降ではパラメータ表の固定値と一致を必須とする |
| `prev_checkpoint_hash` | hex(32B) | 前チェックポイントのハッシュ。seq=0 では 32 バイトのゼロ |
| `chain_state` | hex(32B) | 逐次連鎖の到達状態（§4） |
| `checkpoint_hash` | hex(32B) | 上記全項目から計算するこのチェックポイントのハッシュ（§3.1） |
| `finalized_block_number` | int（任意、v0.2〜） | 観測した finalized ブロック番号。0 以上、`best_block_number` 以下、かつ **2^63−1 以下**（符号化が i64 のため。v0.4、L-02）。品質ゲート（§8.3）に使う。**v0.2 以降のバンドルでこの項目が欠けたチェックポイントは「未 corroborated（裏付けなし）」として重みに数えない**（v0.3、H5） |
| `witness_peer_hashes` | hex(32B) の配列（任意、v0.2〜） | その区間に観測したピア識別子のハッシュ一覧（§9）。**生の識別子は入れない**。ソート済み・重複なしを必須とする |

### 3.1 チェックポイントハッシュ
- v0.1: ドメイン分離文字列 `QDP1/ckpt/v0.1` の後に、以下のバイナリ連結（数値はすべてビッグエンディアン）を SHA-256 したもの:
  `seq u64 | timestamp i64 | best_block_number u64 | best_block_hash 32B | observed_peers u32 | prev_checkpoint_hash 32B | iterations u64 | chain_state 32B`
- v0.2: ドメイン分離文字列 `QDP1/ckpt/v0.2` とし、上記連結の後に `finalized_block_number i64（不在時は -1） | witness件数 u32 | witnessハッシュ 32B × 件数（ソート順）` を続ける。任意項目の「不在」に唯一の正規表現を与えることで、不在と明示的空を区別しない。
- v0.3: 符号化は v0.2 と同一とし、ドメイン分離文字列だけを `QDP1/ckpt/v0.3` に変える（版の異なるハッシュが混同されることを防ぐ）。
- **v0.4: 符号化は v0.2／v0.3 と同一とし、ドメイン分離文字列だけを `QDP1/ckpt/v0.4` に変える**（バイト列契約は Android 実装と完全一致させること）。
- **v0.5: 符号化は v0.4 と同一とし、ドメイン分離文字列だけを `QDP1/ckpt/v0.5` に変える**。

## 4. 逐次ハッシュ連鎖（VDF的部品）とパラメータ表

- ハッシュ関数: **SHA-256**（試作）。理由: 標準ライブラリのみで全環境（VM／Actions／将来の端末実装）で同一結果が得られ、検証が安い。**Poseidon2 はノード統合時の目標**として注記する（チェーンとの同種性は統合段階で得るもので、オフチェーン試作の正しさには影響しない）。
- **パラメータ表（v0.3、C1。v0.4／v0.5 も同じ表を使う）**: チェックポイント間隔と連鎖イテレーション数は、参加者が選ぶ値ではなく、仕様が版ごとに固定する値である。参照実装の定数表 `PARAM_PROFILES` が正本で、本節がその写しである:

  | プロファイル | 用途 | `checkpoint_interval_sec` | `iterations_per_checkpoint` |
  |---|---|---|---|
  | `production` | 本番の生成・検証 | 600 | 1,000,000 |
  | `test` | テストスイート専用（実行時間を短くするため） | 600 | 50 |

  v0.3 以降のバンドルの `params` が、検証側が指定するプロファイルの値と一致しない場合、そのバンドルは検証不合格とする。**プロファイルの選択は検証者・運用者の文脈であり、参加者の入力では選べない**。本番の検証で `test` プロファイルを有効にしてはならない（安い計算で作られたバンドルが本番の重みを得てしまう）。v0.1 / v0.2 バンドルは歴史的互換のため宣言パラメータのまま形式検証できたが、それは明示オプションによるアーカイブ検証の場合に限るようになった（§12）。

- 区間計算（チェックポイント i）:
  1. 種（seed）:
     - v0.1 / v0.2: `seed = SHA-256("QDP1/seed/v0.1" | prev_chain_state 32B | best_block_hash 32B | seq u64be | best_block_number u64be)`
     - v0.3: `seed = SHA-256("QDP1/seed/v0.3" | 公開鍵 32B | ネットワーク識別子 | prev_chain_state 32B | best_block_hash 32B | seq u64be | best_block_number u64be)` — 公開鍵とネットワーク識別子（参照実装の定数 `NETWORK_ID = "quantus"`）を束縛し、計算した連鎖を別のID・別のネットワークへ使い回せないようにする（H2 への部分対応。残余は §7）
     - **v0.4: `seed = SHA-256("QDP1/seed/v0.4" | 公開鍵 32B | ネットワーク識別子 "quantus" | prev_chain_state 32B | best_block_hash 32B | seq u64be | best_block_number u64be | slot u64be | finalized_block_number i64be（不在時は -1） | observed_peers u32be)`** — v0.3 の束縛に加え、**スロット番号・finalized番号・観測ピア数**を束縛する。計算済みの区間を別のスロットへ時刻だけずらして使い回すこと（v0.3 の H-01 の前提の一つ）ができなくなる。ただしこれで連鎖が「経過時間の証明」になるわけではない（§7）
     - **v0.5: 種への入力は v0.4 と完全に同一とし、ドメイン分離文字列だけを `"QDP1/seed/v0.5"` に変える**（v0.5 の変更はスポット応答プロトコル・上限設計・版ポリシーであり、連鎖の計算自体は変えない）
     - `prev_chain_state` は前チェックポイントの `chain_state`（seq=0 ではゼロ32B）
     - ブロックハッシュを種に入れるため、そのブロックが存在する前にこの区間の計算を始めることはできない（作り溜め・先回り計算の防止がこの束縛の目的）
  2. `state = seed` に対して `state = SHA-256(state)` を **N 回逐次** 適用したものが `chain_state`
- 検証: 検証者は各区間を再計算し、`chain_state` の一致、区間同士の接続（前区間の `chain_state` が次区間の種に使われていること）を確認する。検証コストについては §6 の上限と §7 の留保を参照。

## 5. 証明バンドル（エクスポート形式）

JSON（UTF-8）。キー順に依存しないよう、ハッシュ計算時は canonical JSON（キーソート・区切り `,`/`:` 固定）を使う。**16進文字列は正規形（小文字・空白なし・固定長）を必須**とし、比較は常にバイト列で行う（v0.3、M2）。

| 項目 | 内容 |
|---|---|
| `format` | `"quantus-depin-proof"` 固定 |
| `version` | `"0.5"`（現行版。検証側の既定受理はこの版のみ、§12） |
| `device_id` | §2 の導出値 |
| `pubkey` | hex(32B) |
| `created_at_unix` | バンドル作成時刻 |
| `params` | `{hash:"SHA-256", signature:"Ed25519", iterations_per_checkpoint:N, checkpoint_interval_sec:600}`。v0.3 以降では §4 のパラメータ表の値そのもの |
| `checkpoints` | チェックポイントの配列（seq 昇順） |
| `bundle_hash` | v0.1 / v0.2: `SHA-256("QDP1/bundle/v0.1" | canonical_json(bundle_hash と signature を除く全項目))` の hex。v0.3: ドメインを `"QDP1/bundle/v0.3"` とする。v0.4: ドメインを `"QDP1/bundle/v0.4"` とする。**v0.5: ドメインを `"QDP1/bundle/v0.5"` とする** |
| `signature` | hex(64B)。Ed25519 署名。署名対象は版対応のバンドルドメイン文字列と `bundle_hash` のバイト列の連結 |

## 6. 検証手順（検証CLIが実施するもの）

検証は次の順序で行う（v0.3、H8/H9。v0.4 で fail-fast 化、H-05）。**再計算より前に、安く済む検査で弾く**ことが要点であり、**不合格が確定した時点でそれ以降の計算は行わない**:

1. **厳密なスキーマ検証**（再計算の前に実施）: 必須項目の存在と型（整数は bool を除く整数型のみ）、未知フィールドの拒否、16進の正規形と長さ、整数の範囲（`finalized_block_number` は符号化に合わせて 2^63−1 以下、v0.4／L-02）、件数の上限（チェックポイント数 ≤ 200,000、チェックポイントあたりの witness 数 ≤ 512、旧版のイテレーション数上限と検証者の総計算量予算）。v0.3 以降の版では `params` がプロファイルと一致することもここで検査する
2. **版ポリシーの検査**（v0.4、H-02）: `version` が現行版（"0.5"）でない場合、検証者が明示的にアーカイブ検証を指定していない限り、ここで不合格とする
3. `device_id` が公開鍵からの導出と一致すること
4. `bundle_hash` の再計算一致。**不一致なら即座に不合格として打ち切る**（v0.4、H-05）。署名自体は本物（公開済みバンドルの正規の署名）でも、改ざんされた複製で連鎖再計算を強制することはできない
5. **署名検証**（弱い鍵の拒否を含む、§2）。**無効なら即座に打ち切り**、連鎖の再計算には進まない（偽造バンドルで検証者の計算を燃やせない）
6. `seq` が 0 からの連番であること、`prev_checkpoint_hash` の連結、各 `checkpoint_hash` の再計算一致（版に応じた §3.1 の符号化で）、`timestamp_unix` の単調増加、`best_block_number` の非減少、（v0.2〜）`finalized_block_number` の範囲、`witness_peer_hashes` のソート済み・重複なし。ここで不合格があれば連鎖再計算には進まない
7. 各区間の逐次連鎖の再計算一致（`chain_state` と区間接続）

いずれか1つでも失敗すればバンドル全体を不合格とする。検証者は `observed_peers` 等の自称値を「署名された主張」として扱い、それ自体の真実性は本フォーマットの範囲外（テレメトリ等の外部目撃と組み合わせる前提）とする。

## 7. 既知の制限（正直な明記）

本節は主張を実態に合わせて絞るためのものである。**現段階の証明が示すのは「署名され、ブロックハッシュに束縛された観測記録の内部整合性」であって、過去の継続稼働そのものの暗号学的証明ではない。**

- **過去性は証明されていない（H1 の残余）**: `timestamp_unix` はデバイスの自己申告であり、ブロック番号／ハッシュの真正性も、参照実装は実チェーンと照合していない（照合は D2 で GitHub Actions に RPC を接続する段階で実装する前提）。ブロックハッシュは公開情報なので、過去のブロックハッシュ列を使えば「過去に参加していた」ように見えるバンドルを後から作ること自体は可能である。したがって「時間の壁」はバンドル単体では担保されず、**期ごとの提出と集計の履歴（いつの集計でそのバンドルの存在が確認されたか）という運用面で担保される**。将来設計として、期ごとにバンドルハッシュを外部へ刻む epoch コミットメント等を検討する。
- **連鎖計算は「検証可能な遅延」ではない（H2 の残余）**: v0.3 で種に公開鍵とネットワーク識別子を、v0.4 でスロット・finalized・ピア数を束縛し、ID・ネットワーク・スロットをまたぐ使い回しは防いだ。しかし高速なハードウェアは連鎖を短時間で計算できるため、連鎖は経過時間の下限を証明しない。同一IDによる過去分の後計算は上記 H1 の問題に帰着する。
- **時刻ずらし重複（H-01）は集計側でも塞いだ**: v0.3 では、同一の観測列を数秒ずらした多数のバンドルが、集計のマージで別々のチェックポイントとして数えられ、決済日数を水増しできた。v0.4 では連鎖の種へのスロット束縛（§4）に加え、集計のマージが**スロット番号で重複排除**する（§8）。残余として、スロット境界をまたぐ細工で最大で境界近傍の二重化が起こり得る余地は理論上残るが、得られる倍率は定数倍以下であり、成熟上限への到達のような桁違いの水増しはできない。
- **目撃に依存する上限の回避余地（H3 の残余）**: witness リスト自体を省略した参加者は相互目撃の辺を持たず、閉じたクラスタの上限（§9）の対象にならない。**したがって現行のコンパニオン（witness を出さない）が参加する限り、クラスタ上限による Sybil 抑制は働いていない**。「偽装50台で合計2.0」という攻撃シミュレーションの数字は、ファームが相互目撃を申告する条件でのものであり、条件なしに引用してはならない。また、運用を複数IDへ分割する（ペア分割、平方根への分割）ことで得られる利益が残る。これらは現設計では未解決であり、主張してはならない強さである。
- **上限プールの希釈（B3-F1、v0.5 の欠陥・v0.6 で修正）**: v0.5 の上限は成分全体を1つのプールとして比例縮小していたため、正直ノード同士の相互目撃グループへファームが相互辺1本で橋渡しするだけで、最強でない正直メンバーがファームのプール質量に希釈された（敵対テストバッテリで最大 −86% を実測）。v0.6 では上限を**ブロック局所**（§9）に改め、橋渡しの辺はそれ自体がサイズ2のブロックになるため、外来の質量が正直なグループのプールに入ることはなくなった。最小再現・増幅再現ともに正直メンバーの重みが無傷であることを回帰テストで固定した。なお、v0.6 初稿の「帰属（counting assignment）」方式には関節点の逃げ道がランダム化橋渡し検査で見つかり、本番集計に使われる前にブロック係数の最小値方式へ改訂した（§9 の改訂注記）。
- **上限の保証範囲（v0.7、M-08 で正確化）**: ブロック局所上限（§9）が保証するのは、次の3つ**だけ**である（基礎重みを `base_u`、調整後重みを `adj_u`、ブロック B の上限を `cap_B` とする）:
  - (i) **すべてのノードについて `adj_u ≤ base_u`**（上限は重みを増やさない）。
  - (ii) **すべての二重連結ブロック B について、B のメンバーの調整後重みの合計 ≤ `cap_B`**（＝ B の最強メンバーの基礎重みの 2.0 倍）。根拠: B の係数は全メンバーの基礎重みの合計から決まり、各メンバーは B の係数以下の縮小率しか受けないため、合計は上限を超えない。
  - (iii) **全体の調整後重みの合計 ≤ 基礎重みの合計**（(i) の帰結）。
  - **保証しないこと（明示）**: ファーム（攻撃者の支配するノード集合）**全体**の合計に対する上限は、基礎重みの合計を超えては存在しない。**「最強メンバーの2倍」という言い方はブロック単位（および単一ブロックで構成されるクラスタ）でのみ成り立ち、ファーム全体への主張としては撤回する**（v0.6 までの開示はこの点で過大だった）。多数のブロックにまたがるファームは、基礎重みの合計に近づくことができる。その境界例: **全員の基礎重みが 1 の5台が、頂点1つ（h）を共有する2つの三角形 {h, a, b} と {h, c, d} を作ると、各ブロックは合計 3・上限 2・係数 2/3 となり、ファーム合計は 10/3 ≈ 3.333 になる**（「最強の2倍」なら 2 のはずであり、ブロック数に比例して伸びる）。回帰テストでこの数値を固定している。
  - したがって Sybil への実質的な歯止めは上限ではなく**時間の壁**である。ただし時間の壁について言えることは、次の範囲に限る（v0.8、M-06 で正確化。従来の「基礎重みそのものが実デバイスでの継続日数の平方根であり、ファームの合計を伸ばすには台数分の実デバイス×実日数を要する」という言い方は、数学的に裏付けがないため**撤回する**）: **重みは、提出され記録された履歴だけの関数である**。バンドルは、それが別個の物理デバイスから来たことを何ら証明しない。N 個の ID の合計重みは、各 ID の履歴から決まる基礎重みの単純合計を超えては抑えられない（割り引きは §9 のブロック単位でのみ働く）。**バンドル単体は、時間に一切の価格を付けない**（v0.8、設計レビューによる訂正。従来の「時間の壁が ID ごとの壁時計時間に価格を付ける」という言い方も撤回する）: 公開済みの古いブロックハッシュ列から履歴を後計算することは、連鎖の逐次計算コストでも、将来のチェーン照合でも、防げない（ハッシュ列も計算結果も後から作れるため）。時間が重みに入るのは、集計側の2つの仕組みだけである: (i) **first-seen 固定**（§8）— チェックポイントの実効時刻は `max（記録時刻, その内容が集計に初めて現れた時刻）` であり、実効的な存在時刻は「主張された記録時刻」と「集計が実際に目撃した到着時刻」のうち**遅い方**である。したがって、公開済みの古いブロックハッシュ列から後計算した履歴は、初めて提出された時点から実時間が経過するまでは何も稼げない（当初は min 式で設計・実装したが、min では過去方向の後計算を止められないことが実装段階で判明し、2026-11-08 に本人の承認を得て max 式に訂正した）。記録の直後に提出する正直な提出者は first-seen ≈ 記録時刻となり影響を受けない。一方、提出が遅れた履歴については、その時計は実質的に提出日から始まる。これは欠陥ではなく仕様である（集計が目撃していない過去は、重みの根拠にしない）。(ii) **決済待ち**（§8.4）— 実効時刻から7日を経なければ重みに数えない。1台の計算機が複数の ID を並行して育てることは、本形式では検出も禁止もしない。各 ID が集計に対して払うのは、この固定と決済を通過する時間だけであり、「デバイス台数分の実時間」ではない。上限の役割は、単一の塊として相互目撃する集団が「塊の最強者1台分の倍以上」には数えられないようにし、かつ橋渡しによる巻き添え（B3-F1）と基準の貸し借り（R-H02）を防ぐことに限る。
- **上限の残余（v0.6。v0.7 で保証範囲を上記に正確化）**: ブロック局所化後も、次の余地は残る（いずれも主張してはならない強さとして明記する）:
  - **ハブ／スター型トポロジは上限を回避する**: 中心1台＋葉だけの相互グラフでは、すべてのブロックがサイズ2の辺ブロックとなり、サイズ2のブロックは構造的に上限が効かない（上限＝強い方の2倍 ≥ 両者の合計）。したがってスター型ファームは基礎重みの合計のまま数えられる（回帰テストでは51台で合計 51.0）。これは上記「保証しないこと」の内側にある（ブロック単位では (ii) が常に成り立っているが、ファーム合計は基礎重みの合計そのもの）。葉が中心以外とも相互目撃すればブロックは大きくなるが、「葉同士は無関係・中心とだけ相互」という形そのものは現規則では割り引けない。
  - **ファームのブロックへ二重連結に入り込んだ成熟ノードは、そのブロックの上限基準に重みを貸す**: 成熟ノードがファームの塊へ **独立した相互パスを2本以上** 持つ（＝同じブロックのメンバーになる）場合、そのノードの基礎重みがブロックの上限（最強メンバーの2倍）の材料になる。単なる1本の橋渡し辺では貸せなくなったが、二重連結の入り込みは「その集団の一員として振る舞っている」こととデータ上区別がつかない。
  - **二重連結の入り込みは、正直なノード自身の重みも割り引く（巻き添え。v0.8 で数値例を明記）**: 上記の入り込みが起きると、ブロックの係数は全メンバーに等しく効くため、正直なノード自身も割り引かれる。具体例: 基礎重み 10 の正直ノードが、基礎重み 1 の Sybil 20 台からなるクリークへ相互辺2本で同じブロックに入ると、ブロック合計は 30（10＋20×1）、上限は 20（最強 10 の2倍）、係数は 2/3 となり、正直ノードの調整後重みは 10 × 2/3 ＝ 20/3 ≈ 6.67 に減る。保証 (ii) 自体は保たれる（ブロック合計は上限以下）が、「正直なノードは無傷」という保証は、ブロックを共有する限り成り立たない。v0.7 までは「基準を貸す」側面だけを記し、この巻き添えを開示していなかったため、v0.8 で是正する。
  - **v0.5 で明記した「成熟ノード2台の橋渡し」残余は、上記に置き換わる（superseded）**: 2台の成熟ノードがそれぞれ辺1本で集団に橋渡しするだけでは、もはやどちらの重みも集団の上限基準には入らない。残るのは二重連結の入り込みだけである。
  - 将来の対策候補として、目撃の辺に継続性・共観測の重みを持たせる（単発の相互言及ではなく、長期間にわたって互いを観測し続けた辺だけを上限の材料にする）設計を引き続き検討する。これが入れば、ハブ／スター型や二重連結の入り込みについても、辺の「実績」で割り引く余地が生まれる。
- **プライバシー（M3）**: witness ハッシュは、参加者の識別子を知る者には照合可能であり、チェックポイントの時刻列とあわせて活動パターンや関係性が集計者に見える。生IDを晒さないだけで、匿名性までは提供しない。
- **署名実装（M4）**: 純Python Ed25519 は定数時間でなく、本番秘密鍵向きではない（§2 の留保も参照）。
- **チェーン照合の自動化は未実施**: best ハッシュの実在確認やスポットチェック期待値の計算はチェーン側データが要るため、参照実装の範囲外（D2 で実装）。現段階の集計器は導出の一致と、運用者が別途渡した信頼済み期待値との照合までを担う。
- 実チェーンでは短い再編成（reorg）で best が後退し得るが、参照実装は厳密モードとして `best_block_number` の減少を失敗扱いにする。実データ適用時に許容幅を再設計する。
- **検証コストの非対称性（v0.7、H-02 で正確化。v0.8 で内容キーの正規化と延期への置換）**: かつて「検証コスト = 生成コスト」と書いたが、これは再包装に対して成り立たない。連鎖そのものは生成に1回計算すれば、 `created_at_unix` を変えて再署名するだけで何度でも「新しいバンドル」として提出でき、検証側が都度全区間を再計算するなら、攻撃者は生成1回分のコストで検証側に K 倍の計算を強制できる。集計器はこれを次の形で抑える: (1) 連鎖検証の結果は**内容キー**で再利用し、再包装コピーは署名検査（提出ごと）だけで済ませる。v0.8 では内容キーを**検証器の正規化済み構造**から計算する（§8、段B）ため、検証器が区別しない表現の違い（任意項目の省略と明示的な空値、キー順）は同一のキーに潰れる。v0.7 のキーは提出された生の辞書をハッシュしていたため、チェックポイント C 件について witness の省略／明示的な空リストで 2^C 通りのキーが分岐し、1つの連鎖に何度も全検証を強制できた（新H-02）。(2) 1回の集計で連鎖検証する相異なる内容キーの総数には安全弁を設けるが、超過分は**却下ではなく延期**とする（§8）。v0.7 の却下式の予算は、失敗したキーでも枠を消費する設計だったため、署名済みのゴミを先に検証させることで真正な提出を却下させる排除の手段になった（新H-01）。これでも、正規の相異なる長期バンドルの検証コスト自体は残る（全区間再計算が連鎖検証の本体である）。長期バンドルではスポットチェック検証モードの追加が要る。旧版バンドルには検証者の総計算量予算（§6）がある。v0.4 の fail-fast は「不合格バンドル」に対する浪費を止めるものである。**捏造入力に対しては「生成と検証のコストは対称」という主張自体が成立しない**（v0.8、設計レビュー）: `chain_state` を偽造したバンドルは、偽造者は逐次計算を一切払わずに作ることができ、検証者だけが全区間の再計算（production では1チェックポイントあたり100万回）を払う。したがって検証の総作業量を制限する責任は集計器ではなく、**集計の入口層**（パイロット側の提出経路の制限）にある。集計器が提供するのは、内容単位の検証再利用と、デバイス単位の公平性（延期の繰越とラウンドロビン、§8）までである。

## 8. スコアリング（集計器の規則）

提出は「バンドル＋提出メタデータ（GitHubアカウント名、アカウント年齢日数、提出時刻）」の組とする。提出メタデータは**表示専用**であり、重み・適格性・失格の根拠には一切使わない（v0.3、C2）。アカウント年齢日数も参考情報として記録するだけである（§8.2、v0.2 改訂）。集計器は検証（§6）を通過した**現行版（"0.5"）のバンドルだけ**を対象に、以下の規則でノードごとの **生の台数寄与（raw_count、正常なら1）** と **調整後重み（adjusted_weight）** を出す。旧版バンドルは検証の成否にかかわらず集計対象外とし、帰属なしで却下して理由を記録する（v0.4、H-02、§12）。表示の主指標は調整後重みとし、生の台数も併記する。

- **集計時刻（v0.3、H4）**: 集計時刻 `scored_at` は呼び出し側（運用者）の信頼できる時刻のみを使う（未指定なら集計実行時の現在時刻）。**提出メタデータや入力ファイル内の時刻からは絶対に導出しない**。未来日付の提出で決済待ち（§8.4）を飛ばすことはできない。
- **提出の隔離（v0.3、H9。v0.4 で CLI 読込側にも拡張、M-03）**: 提出は1件ごとに隔離して処理し、壊れた提出が混ざっても集計全体は完走する。提出ファイルの読み込み・JSON パースの失敗も、提出ごとの却下として理由つきで記録し、全体を止めない。検証不合格の提出は「却下」として理由つきで記録される（§10）。**JSON の取り込みは厳密でなければならない（v0.8、L-01）**: バンドルおよびスポット関連の JSON を読む経路では、JSON の定数ではない NaN／Infinity と、オブジェクトキーの重複を、読み込み時点で拒否すること。実装言語の標準パーサがこれらを黙って受理する場合（Python の json は NaN を浮動小数点として通し、重複キーは後勝ちになる）、その差は実装間の判定の食い違いになる（Android 実装のパーサは両方を拒否する）。読み込み時点の拒否は、提出ごとの却下として上記の隔離の規則で記録する。
- **検証は二段構えであり、却下は提出にだけ帰属する（v0.7、H-01。v0.5 の R-H01 を継承・拡張）**: 提出の処理は次の順序とする。
  1. **軽い構造検査と `bundle_hash` の再計算**: `bundle_hash` が64文字の小文字 hex、`checkpoints` が配列であること。再計算（canonical JSON の1パス、連鎖計算は含まない）との不一致は即却下。
  2. **完全な重複の判定**: 署名を含む提出内容がバイト列として同一の提出は、1回だけ処理する。再提出は重複として数え（受理・却下いずれの結果も引き継ぐ）、**連鎖の再計算を決して引き起こさない**（R-H01 の維持）。受理済みバンドルの重複提出が持つスポット応答レコードは、従来どおり応答プールに加える（§11）。
  3. **段A（提出ごとの認証）**: §6 の手順 1〜5（厳密なスキーマ検証、版ポリシー、 `device_id` の束縛、`bundle_hash` の再計算、署名検証）を、**その提出そのもの**に対して行う。段Aの失敗は**その提出だけに帰属**させ、内容のハッシュには記録しない。署名は `bundle_hash` の計算対象外であるため、署名だけを壊したコピーは真正コピーと同一の `bundle_hash` を持ち得るが、その却下は壊れたコピー自身にだけ付き、真正コピーは提出順にかかわらず自身の署名で認証される。**v0.6 までは却下状態を `bundle_hash` に紐付けて保持していたため、署名を壊したコピーが先に処理されると後続の真正コピーが検証なしに捨てられた（提出順に依存する排除、H-01）**。v0.7 ではこの紐付けを廃止した。
  4. **段B（内容キーごとの連鎖検証）**: §6 の手順 6〜7（チェックポイントハッシュ・連結・逐次連鎖の再計算）は、**内容キー**単位で1回だけ行い、結果を再利用する。内容キーは、連鎖を決定する全内容（公開鍵、形式、検証プロファイル、`prev_checkpoint_hash` 連結を含むチェックポイント列全体）から計算するハッシュであり、**署名と `created_at_unix` を含まない**。したがって `created_at_unix` だけを変えた再包装コピーは、それぞれ段Aの署名検査は受けるが、段Bの連鎖検証は共有する（H-02）。内容キーが相異なる場合に限り、新しい連鎖検証が走る。**内容キーは、検証器自身の正規化済み構造から計算しなければならない（v0.8、新H-02）**: 段Bの検証が使う正規化（§6 手順1のスキーマ検証が作る正規形。任意項目の不在は既定値に畳まれ、キー集合は固定される）と同一の正規化を、鍵の計算にも使うこと。提出された生の表現をハッシュしてはならない。検証器が区別しない表現の違い（`witness_peer_hashes` の省略と明示的な空リスト、オブジェクトのキー順）でキーが分岐すると、同一の連鎖に複数のキーが付き、再利用が崩れる（v0.7 のキーは生の辞書をハッシュしており、チェックポイント C 件で 2^C 通りに分岐した）。正規化の出所は1つだけとし、検証と鍵計算で共有する。段Bの合否は（失敗の verdict を含めて）集計の実行内では内容キー単位で保持し、同じ連鎖は再検証しない。
  5. **受理の条件**: 提出が受理されるのは、その提出自身の段Aが合格し、かつその内容キーの段Bが合格した場合に限る。スポット応答レコードのプール（§11）には、受理された提出からのレコードだけを入れる（段Aを通っていない提出のレコードは、失格にも合格にも使わない）。
- **検証総量の安全弁と延期（v0.8、新H-01。v0.7 の「集計の予算」は廃止）**: v0.7 は検証量に却下式の上限を設けていたが、却下を伴う上限はそれ自体が排除の手段になる: (i) 全体の内容キー上限は失敗したキーでも消費されたため、署名済みのゴミ連鎖を先に検証させることで、後から来た真正な提出を「予算超過」で却下できた。(ii) デバイスごとの提出数上限は、被害者の公開済みバンドル（署名は公開情報である）を再提出するだけで本人の枠を消費できた。したがって v0.8 では**却下を伴う上限をすべて廃止**し、次に置き換える:
  - **デバイスごとの受理対象提出数に上限は置かない**。段Aを通過した提出の受理・却下は、その内容キーの段Bの結果によってのみ決まる。
  - **連鎖検証の総量には安全弁を置く**: 1回の集計で段Bの連鎖検証を行う相異なる正規化済み内容キーは最大 **512 件**（設定可能）までとする。安全弁を超えたキーを持つ提出は、その回の集計では検証せず、結果に **「延期（deferred）」** として理由つきで記録する。**延期は却下ではない**: 延期の事実は提出にも ID にも記録されず累積しない。後の回の集計に回せば、通常どおり処理される。
  - **検証順は公平順であり、到着順には依存しない（v0.8、設計レビュー A2）**: 前回の集計から繰り越された延期分のキー（繰越クラス）を**先に**検証し（繰越クラス内は内容キーの辞書順）、残りの枠を新規キーに**デバイス間のラウンドロビン**で分ける（デバイスは device_id 順、各デバイスのキーは辞書順、1巡に1件ずつ）。辞書順だけでは、より小さいキーを毎回先行させることで特定のキーを永久に延期させることができるため、この順序にする。繰越分のキーは、集計の呼び出し側が前回の結果（deferred の内容キー）を渡すことで指定する。
  - **延期が残る回の結果は未確定（provisional）である（A3）**: 延期されたノードは他のノードのクラスタ上限（§9）を変え得るため、延期が1件でもある回のスコアは確定値として扱わない。結果のサマリに `complete: false` と延期件数を明示すること。
  - **失敗 verdict のキャッシュの範囲（A5）**: 段Bの合否は内容キー単位で保持し、同じ連鎖を1回の集計で再検証しない。ただしキャッシュしてよいのは、検証が完走して得た**決定的な内容 verdict**（合格・不合格）だけである。検証の中断・タイムアウト等の非決定的な失敗は「不合格」として記録せず、そのキーは延期として扱う。参照実装のキャッシュは集計の実行内に限る。実行をまたいで verdict を永続化する場合は、パイロット側で規則世代（本仕様書の版）に紐付けて管理すること。
  - 提出が却下されるのは、その提出自身の段Aの失敗、またはその内容の段Bの失敗が確定した場合だけである。他者の提出・他者の失敗・到着順によって、真正な提出が却下されることはない。
- **実効時刻と first-seen 固定（v0.8、設計レビューによる原則4の訂正）**: バンドル単体は時間に一切の価格を付けない（§7）。時間が重みに入るのは集計側だけであり、その入口の1つが本項である: チェックポイントの**実効時刻**を `max（記録時刻, その正規化済み内容が集計に初めて現れた時刻）` と定義し、成熟（§8.2）と決済（§8.4）の計算はすべて実効時刻で行う。実効時刻は2つの時刻のうち遅い方であり、後計算された履歴は、初めて現れた時刻から実時間が経過するまで成熟も決済も進まない。記録の直後に提出する正直な提出者は first-seen ≈ 記録時刻で影響を受けず、提出の遅れはそのまま時計の開始の遅れになる（仕様。当初の min 式は過去方向の後計算を止められず、2026-11-08 に本人の承認で max 式に訂正した）。「初めて現れた時刻」は、その回の集計で受理された提出のうち、そのチェックポイントの内容（checkpoint_hash で識別する）を含むものの `submitted_at_unix` の最小値とする（提出メタデータのうち、この項目だけは運用側の到着記録として意味を持つ。重み以外の適格性・失格には使わない）。到着記録がない提出（`submitted_at_unix` が未設定・0以下）は固定に寄与せず、その場合の実効時刻は記録時刻のままである。固定は実行をまたいで永続化するのが本来の形であり（パイロット側で内容キーに紐付けて保持する）、参照実装の範囲は「その回の受理提出からの固定」までである。
- **数値の決定性（v0.7、L-01）**: 集計の浮動小数点の合計（ブロック係数の計算、調整後重みの総和など）は、メンバーを決定的な順序（デバイスIDのソート順）に並べ、誤差の少ない合算（参照実装では `math.fsum`）で行う。同一の提出集合に対する集計結果は、プロセスのハッシュシード（`PYTHONHASHSEED`）に依存せず、バイト列まで一致しなければならない。集合の走査順に依存する合算は不具合である。
- **同一デバイスの複数バンドル（v0.3、M1。v0.4 でスロット単位に変更、H-01）**: 同一デバイスの有効なバンドルが複数ある場合、チェックポイントを決定的な順序（先頭時刻、bundle_hash）でマージして集計する。**重複排除の単位はスロット番号（§3）であり、同じスロットに属するチェックポイントは先勝ちで1回だけ数える**。秒単位の時刻がずれていても同一スロットなら二重計上しない。

### 8.1 事実の壁 — 評価対象は照合できる項目だけ
- 重みに入るのは、公開チェーンの事実と照合できる項目（ブロック番号／ハッシュの進行、finalized 遅れ）と、署名・連鎖で束縛された観測記録だけである。
- `observed_peers` 等の自己申告値は **表示と異常検知（§8.5）のみに使い、重みには一切使わない**。

### 8.2 時間の壁 — 成熟関数と減衰
記号: 固定スロット秒数 `SLOT`（§4、現行 600 秒）、マージ後（スロット重複排除後）のチェックポイント総数 `C`、先頭・末尾の時刻 `T0, T1`（いずれも**実効時刻**。§8 の first-seen 固定、すなわち記録時刻と集計が初めて見た時刻のうち遅い方を適用した後の値）。
- **稼得日数は参加者が選ぶ値から計算しない（v0.3、C1）**: 日数は「ゲート通過チェックポイント数 × `SLOT`」からのみ得る。バンドルの宣言した `checkpoint_interval_sec` は重み計算に使わない。
- 期待件数 `E = floor((T1 - T0) / SLOT) + 1`、**継続率（coverage）** `cov = min(1, C / E)`
- 品質ゲート通過件数 `G`（§8.3）と、そのうち決済済み件数 `S`（§8.4）から
  - `決済日数 D = S × SLOT / 86400 × cov²`（欠落は二乗で効く減衰）
- **成熟関数**: `sqrt(min(D, 365))` — 継続日数に対する非線形（平方根）で、上限は 365 日分。量産した新規IDは、**1件ごとの重み** は平方根で小さい。ただし**合計については何も言えない**: N 件の ID の合計は、各基礎重みの単純合計まで伸び得る（§7）。「束ねても伸びにくい」という言い方はしない（v0.8、M-06）。
- 基礎重み `W0 = sqrt(min(D, 365))`
- **時間の壁は「参加の継続日数」だけで作る**（v0.2 改訂）: v0.2 初版にあったアカウント年季係数（GitHubアカウント年齢による係数）は廃止した。外部アカウントの年齢で二重に絞ると参入の壁になり、正直な新規参加者を遠ざけるためである。アカウント年齢は提出メタデータに参考情報として残してよいが、重み・適格性には一切影響させない。「作りたてIDが束になっても長期の正直な1台に届かない」という性質は **主張しない**（v0.8、M-06 で撤回）。反例: witness を申告しない作りたてID 14 件が各1日分の決済済み履歴を持てば、その合計は 14 × sqrt(1) ＝ 14 であり、180 日の正直な1台の sqrt(180) ≈ 13.416 を上回る。成熟曲線（平方根）と決済待ち（§8.4）、閉じたクラスタの割り引き（§9）の組み合わせが実際に与えるのは、1件ごとの重みの小ささと、ID ごとに、集計がその内容を初めて見た時点（first-seen）から数える壁時計時間と決済待ちを払わせることだけであり、合計の上限ではない（§7 の「時間の壁について言えること」を参照）。ただしその前提として §7（過去性はバンドル単体では証明されない。時間の壁は提出履歴という運用面とセットで初めて意味を持つ）を参照。
- 継続率が 0.80 未満のノードには `low_continuity` の旗を立てる（重み式には cov² で既に反映済み）。

### 8.3 品質ゲート（区間の無効化）
- チェックポイントに `finalized_block_number` がある場合、`best - finalized > 300`（ブロック）の区間は **無効** とし、`G` に数えない。
- **v0.2 以降のバンドルで `finalized_block_number` がない区間は「未 corroborated」として無効** とし、`G` に数えない（v0.3、H5。ゲート回避のために項目を落とす手は使えない）。
- 旧版バンドルはそもそも集計対象外である（v0.4、§12）。本節のゲートは現行版バンドルに適用される。

### 8.4 決済待ち（遅延付与）
- 集計時刻から見て **7 日以内** のチェックポイントは未決済とし、`S` に数えない。短期の荒らしは重みになる前に時間がかかる。集計時刻の出どころは §8 冒頭（H4）のとおり。

### 8.5 異常検知（旗立て）
以下の集団には自動で旗を立て、理由と共に結果 JSON に出す（旗自体は失格ではない。§9 のクラスタ割り引きと §10 の失格とは別扱い）:
- `synchronized_start`: 3台以上が同一の開始時刻を持つ
- `identical_peer_pattern`: 3台以上が同一の `observed_peers` 列を持つ
- `settlement_pending`: 末尾チェックポイントが決済待ち期間内にある

## 9. 相互目撃（中継の実在の裏付け）

- ピア識別子（相手ノードの `device_id` または libp2p ピアID）のハッシュは `SHA-256("QDP1/peer/v0.2" | 識別子のUTF-8バイト列)` とする（ドメイン文字列は形式の版と独立に安定させる）。チェックポイントにはこのハッシュだけを入れる（生IDを晒さない、プライバシー配慮。ただし §7 の M3 の留保どおり匿名性までは提供しない）。
  - ここで言うピアIDは**文字列としての識別子**であり、その由来の鍵種には依存しない。なお §2 の訂正どおり、Quantus の libp2p ピアIDは Dilithium 鍵由来であり、Ed25519 とは無関係である（v0.2 の §9 はピアIDの文字列をハッシュ化する方式自体は鍵種に依存しないため、方式は維持する）。
- **目撃として使うのは、品質ゲート（§8.3）を通過したチェックポイントに由来する witness だけ**である（v0.3、H3）。無効な区間の目撃は辺の材料にしない。
- 集計側は、参加者全員の識別子について同じハッシュを計算し、各バンドルの `witness_peer_hashes` と突き合わせる。**A のリストに B が含まれ、かつ B のリストに A が含まれる場合に限り、A–B 間に「相互目撃の辺」がある** とする。片方向だけの言及は裏付けにしない。
- **クラスタの単位は相互辺だけで作る**（v0.4、H-03）: 連結成分は相互目撃の辺のみで構築する。相互辺でつながる成分は構造的に「閉じている」（成分の外への相互辺があれば、その相手も成分に入るため）。v0.3 では成分を片方向の言及を含むグラフで作り、閉鎖性を相互辺で判定していたため、攻撃者が正直な相互ペア同士を片方向の言及でつなぐだけで全員を上限の対象に巻き込むことができた。v0.4 では**片方向の言及は重みに一切影響しない**: 成分にも上限の計算にも入らない。
- 閉じたクラスタ（＝相互辺の連結成分）には割り引きを掛ける。**上限は v0.6 でブロック局所化した（B3-F1）**。規則は次のとおり（独立実装が同じ結果を出せるよう、手順をすべて定める）:
  1. **ブロック分解**: 成分を、相互グラフ上の**頂点二重連結成分（ブロック）**に分解する（Tarjan の関節点アルゴリズムによる。ブロックとは、頂点を1つ取り除いても分断されない極大な部分グラフであり、橋の辺はそれ自体がサイズ2のブロックになる）。実装は反復型とし、頂点・辺の処理順はデバイスIDのソート順で決定的にすること。
  2. **ブロック係数（帰属は置かない）**: ブロック B の上限は `cap_B = 2.0 × max{基礎重み : B の全メンバー}` とする。B の**全メンバー**の基礎重みの合計が `cap_B` を超える場合、B の係数は `factor_B = cap_B / 合計`、超えなければ `factor_B = 1.0` とする。**「帰属（どのブロックに数えるか）」という概念は置かない**: 関節点であるメンバーも、自分を含むすべてのブロックの合計と上限の計算に常に入る。
  3. **頂点の縮小率は、自分のブロック係数の最小値**: 頂点の調整後重みは「基礎重み × 自分を含むすべてのブロックの係数の最小値」とする（どのブロックでも効いていなければ 1.0。旗 `closed_cluster_discount` は縮小率が 1.0 未満の頂点に付け、サマリの `closed_clusters_capped` は係数が 1.0 未満のブロック数を数える）。根拠は2つある: (i) ノードの重みは「自分が属する最もタイトなクラスタ」によって割り引かれるべきものであり、より緩い構造に属することが、最もタイトな割り引きを緩めることは決してない。(ii) どのメンバーも、自分の属するブロックの計算から逃れることはない。
  4. **サイズ2のブロックは特別扱いしない**: 上限（強い方の 2.0 倍）は両メンバーの基礎重みの合計以上に常になるため、数式のままで決して効かない。橋の辺がサイズ2のブロックになることが、後述の「橋渡しで他人のプールに入らない」性質の根拠である。
  - **保証の範囲（v0.7、M-08）**: この規則が保証するのは §7（上限の保証範囲）の (i)〜(iii) だけである: 各ノードの調整後重みは基礎重み以下、各ブロックのメンバーの調整後重みの合計はそのブロックの上限以下、全体の合計は基礎重みの合計以下。**「最強メンバーの2倍」はブロック単位の上限であり、ファーム全体・成分全体の上限ではない**。多数のブロックにまたがる集合の合計は基礎重みの合計に近づき得る（境界例は §7 の2三角形の例を参照）。成分全体を1つのプールとして縮小する規則に戻すと B3-F1（橋渡しによる正直メンバーの希釈）が再発するため、全体上限が要るならブロック間で再使用できない予算配分等の別設計が要る（将来課題）。
  - **v0.6 改訂注記（帰属方式の廃止）**: v0.6 の初稿では「各頂点は、自分を含むブロックのうちちょうど1つに帰属する」という数え方（counting assignment、帰属先は自分以外のメンバーの基礎重みの最大値が最も小さいブロック）を採用していた。しかし初稿に対して行ったランダム化橋渡し検査で、**関節点の逃げ道**が見つかった: ファームのクリークのメンバーが正直ノードへ相互辺1本で橋渡しすると、そのメンバーはクリークのブロックではなく、決して効かないサイズ2の橋ブロックに数えられるため、(i) 自身はクリークの上限の外で基礎重みを満額保持し、(ii) クリークの被計算合計が減って残りのメンバーの縮小が緩み、(iii) 対称に、正直なクラスタのメンバーも橋渡しによって自クラスタの割り引きから逃げられた（検査実測: 橋渡し1本でファーム合計 8.0 → 10.77、正直側の重みも両方向に変動）。このため帰属を廃止し、上記のブロック係数＋最小値ルールに置き換えた。**この置き換えは、v0.6 の規則が本番集計に一度も使われる前に行われた**（v0.6 の規則で確定した集計結果は存在しない）。回帰テストは、単一辺の橋渡しに対する双方向の不変性（正直側の重みもファーム合計も、橋渡しの有無で変わらない）を決定的ケースとランダム化ケースの両方で固定している。
  - この形にした理由（設計の履歴）: v0.4 の基準は「最も重い1台」であり、ファームが成熟した正直ノード1台と相互辺1本をつなぐだけでその重みを自らの上限に取り込み（再現値: ファーム合計 2.0000 → 21.1561）、正直なノード自身まで減額できた（13.4164 → 5.6768、R-H02）。v0.5 は基準を「2番目に重いメンバー」に変えてランドリングは塞いだが、成分全体を1つのプールとして縮小するため、橋渡しされた正直グループの最強でないメンバーがファームの質量に希釈される欠陥（B3-F1、最大 −86%）が残った。v0.6 のブロック局所化では、正直なグループとファームの塊は別のブロックに分かれ、互いのプールに入らない。元の R-H02 攻撃はファーム合計 2.0000・正直ノード 13.4164 のまま、B3-F1 の最小再現・増幅再現では正直メンバーが全員無傷であることを回帰テストで固定した。残余（ハブ／スター型の回避、二重連結で入り込んだ成熟ノードの基準貸し）については §7（上限の残余、v0.6）を必ず併記すること。
- 参加者でないピアへの言及（ハッシュが誰にも一致しない）は、裏付けにも割り引きの根拠にもしない。相互目撃が効くのは相手も参加者の場合に限る、という限界をここに明記する。残余の回避余地については §7（H3 の残余）を参照。

## 10. 失格規則（時間の没収）と却下

失格は **「有効な署名を持つ証拠」がある場合に限る**（v0.3、C2。v0.4 でスポット応答自体の署名を必須化し、この原則を応答の真正性にも及ぼした、C-01）。具体的には次の1つだけである:

1. **スポットチェック不合格**（§11）: 運用者が別途の信頼済み経路で渡した期待値と、**バンドルのID鍵で署名され検証に合格した応答**が一致しない場合。その ID は **履歴全体を失効** とする（生の台数寄与・調整後重みはともに 0、理由を結果に明示する）

それ以外は失格にしない:

- **未署名・署名不正のスポット応答は「本人の応答」として扱わない**（v0.4、C-01。v0.5 でプロトコル v2、§11）: 応答レコードはバンドルの外側にあるため、誰でも他人のバンドルの複製に偽の応答を添付できる。署名が検証できない応答は無視して旗を立てるに留め、失格の根拠には絶対にしない。必須項目（`target_seq`／`revision`）を欠くレコードも同じ扱いとする。
- **検証不合格のバンドルは「却下」であり、失格ではない**: 不合格のバンドルが主張する ID は何の根拠にもならない（署名が検証できていない以上、その ID の持ち主の行為とは言えない）。却下は帰属なしで記録し、その ID の他の有効な提出には一切影響しない。他人のバンドルの改ざんコピーを提出して被害者を失格させることはできない。**旧版バンドルの提出も却下（帰属なし）であり、失格ではない**（§12）。
- **却下はその提出だけに帰属する（v0.7、H-01）**: 二段検証（§8）では、段A（署名を含む提出そのものの認証）の失敗は、その提出についてだけ記録する。同じ内容の別のコピーは、それ自身の署名で独立に判定され、**提出の順序によって結果は変わらない**。署名だけを壊したコピーを先に提出しても、真正なコピーは影響を受けない。逆も同様で、真正なコピーの受理が、壊れたコピーを受理させることもない。
- **延期は却下でも失格でもない（v0.8、新H-01）**: 集計の安全弁（§8）を超えた提出は「延期（deferred）」として記録される。延期はその回の集計の都合であり、提出の内容についての判定ではない。延期された提出は後の回で通常どおり処理され（繰越クラスとして優先される、§8）、延期の事実が提出や ID に累積することはない。延期が残る回の結果は未確定（provisional）であり、確定値として扱わない（§8）。
- **同一バンドルの再提出は冪等**: 署名を含む提出内容が同一の再提出は重複として無視し、1回だけ数える（提出したアカウントが違っても同じ）。使い回しは失格事由から外した。再提出で連鎖の再計算は行わない（§8、R-H01）。ただしスポット応答レコードは、受理された提出（その重複分を含む）から収集する（本人の署名済み応答のうち最大の revision が効くため、訂正応答が重複提出に乗って届いても正しく評価できる、§11）。認証されていない提出のレコードはプールに入れない（§8）: 却下された提出に添付されたレコードが、失格にも合格にも使われることはない。
- **「同一鍵の複数デバイス主張」の規則は削除した**: `device_id` は公開鍵から機械的に導出されるため、同一鍵が複数の `device_id` を主張することは構造的に起こり得ない。起こり得ない規則は根拠のない失格の余地にしかならないため、置かない。
- **提出メタデータ（アカウント名・アカウント年齢・提出時刻）は失格の根拠にしない**。表示専用である。

お金を賭けさせる代わりに、育てた時間（継続の蓄積）を失わせることが罰になる、という設計は維持する。再登録は新しい鍵＝ゼロからの再出発になる。ただし罰の発動は上記の署名つき証拠に限る、というのが v0.3 以来の線引きである。

## 11. スポットチェック（データ所持の抜き打ち）

1. **指名の導出**: その期の提出締切**後**に確定する「将来のファイナライズ済みブロックハッシュ」 `Hc`（提出時点では誰にも予測できない）を種にし、対象チェックポイントの番号を決定的に導出する:
   `target = int(SHA-256("QDP1/spot/v0.2" | Hc 32B | チェックポイント総数 u64be)) mod チェックポイント総数`（ドメイン文字列は導出方式の識別子として安定させる）
2. **応答と期限**: 指名されたノードは、そのチェックポイントが束縛するブロックについて、データ由来値 `SHA-256("QDP1/spot/v0.2" | "/value" | block_hash 32B | ブロック本体バイト列)` を提出する。**応答の締切は、指名が確定した後に別途定める「応答締切」**であり、提出締切とは別の時刻である（v0.3 で矛盾を修正: v0.2 は「応答も提出締切まで」と書いていたが、指名は提出締切後でないと導出できないため両立しなかった）。運用上は次の期の提出締切を応答締切にするのが自然である。
3. **応答の署名（プロトコル v2、v0.5。C-01／R-C01／R-M05）**: 応答レコードは `{response, signature, target_seq, revision}` の形とし、**バンドルの ID 鍵による署名を必須**とする。`target_seq` と `revision` は**必須の項目**であり、正確な整数（bool は不可）で、`target_seq >= 0`、`revision >= 0` でなければならない。**`response` と `signature` は小文字の正規形 hex（偶数長、`0-9a-f` のみ）でなければならない（v0.6）**。バンドル本体の hex 項目は §5 で正規形を必須としており、スポット記録だけが大文字 hex を受理する非対称は「同じバイト列に2つの符号化が通る」曖昧さになるため揃えた。大文字・混在ケースの hex を持つレコードは、署名の検証以前に「未署名」として扱う（無視し、失格には使わず、単独で合格にもしない）。署名対象のバイト列は
   `"QDP1/spot-resp/v0.5" | bundle_hash 32B | Hc 32B | response 32B | target_seq i64be | revision u64be`
   とする（バイト列契約は Android 実装と完全一致させること）。集計器は応答レコードを、**受理された提出（その重複分を含む）から収集**し、次の規則で評価する（v0.7 で §8 の二段検証に合わせて明確化: 却下された提出のレコードはプールに入らない）。**収集の際、応答プールは指紋で重複排除する（v0.8、M-05）**: 指紋は**応答レコード全体の正規形ハッシュ**であり、完全に同一のレコードだけが重複として落ち、署名検証は1回だけ行われる。指紋を（bundle_hash＋署名）のような部分集合にしてはならない（設計レビュー A1）: 署名をコピーして本文を書き換えた偽応答が本物の訂正応答と同じ指紋になると、先に収集された偽応答がスロットを占有し、本物の応答が検証前に重複として消える（R-C01 の再来になる）。偽応答はそれ自身の指紋を持ち、それ自身の署名検証の失敗によって無視されなければならない。
   - **署名がバンドルの公開鍵で検証でき、必須項目を満たすレコードだけ**が本人の応答である。署名のない・検証できない・項目の欠けたレコードは無視して旗（`spot_check_unsigned_ignored`）を立て、**失格には絶対に使わない**。
   - 本人の応答が複数ある場合は、**最大の `revision` を持つものだけ**が効く（提出順には依存しない）。所有者は応答を訂正するたびに `revision` を増やして署名し直す。古い revision の応答を第三者が再送しても、判定は反転しない。
   - 最大 revision の応答のうち `(response, target_seq)` の組が複数種類ある場合は、所有者自身の**二重応答（equivocation）**として不合格とする。
   - 選ばれた応答について、`target_seq` が導出値（項目1）と一致し、かつ `response` が信頼済み期待値と一致した場合に合格とする。どちらか一方でも食い違えば不合格（§10 の失格）。
   - **なぜ v2 が要ったか**: v0.4 の署名は「`target_seq` 不在」を i64 の -1 で符号化しており、明示的な `target_seq: -1` とバイト列が同一だった。一方で評価側は両者を違って扱ったため、本人が正しく署名した応答に第三者が `"target_seq": -1` を追加するだけで、署名は有効なまま失格証拠に化けた（R-C01）。また署名の内側に順序がなかったため、本人が訂正した後でも、古い不一致応答の再送で判定を反転できた（R-M05）。v2 は「不在」の符号化自体を廃し、順序（revision）を署名の内側に入れることで両方を閉じた。
4. **判定と期待値の出どころ（v0.3、H7）**: 期待値は、**運用者が提出レコードとは別の信頼済み経路で渡した場合にのみ**照合する。提出レコード内に書かれた期待値は絶対に読まない（自己認証を防ぐ）。信頼済み期待値がない場合は、そのスポットチェックは **「未実施」として記録し、失格にも合格にもしない**。署名済みの応答がない場合は旗を立てるに留め、失格にしない（失格は、署名済み応答が期待値と不一致という積極的な証拠がある場合だけ、§10）。期待値の自動計算にはチェーン側データへのアクセスが要るため、公開チェーンとの自動照合は D2（GitHub Actions に RPC を接続する段階）で実装する。

## 12. 互換性（版ポリシー）

- バンドルは `version` フィールドで形式の版を識別する（現行: "0.5"。過去: "0.1" / "0.2" / "0.3" / "0.4"）。
- **仕様書の版と形式の版は別である**: 本仕様書は v0.8 だが、形式の現行版は "0.5" のままである（v0.6・v0.7・v0.8 は規則改訂であり、形式の変更・データ移行はない。冒頭の注記を参照）。形式の版ポリシーは本節のとおり v0.5 から変更しない。
- **検証の既定は現行版のみ受理する**（v0.4、H-02）: v0.3 までの方針（旧版も宣言パラメータのまま検証し、集計規則だけ現行化する）は、新規に作った旧版バンドルで現行版の防御（固定パラメータ表、公開鍵・ネットワーク束縛、品質ゲート）を丸ごと迂回できる穴になっていた。そのため方針を変更する。
- **旧版バンドルの検証は、検証者が明示オプション（参照実装では `allow_legacy=True`、CLI では `--allow-legacy`）を指定した場合に限る**。これは過去のバンドルを資料として読み直すためのアーカイブ用途であり、その検証結果を集計・重み付けに使うことはしない。旧版の検証手順自体（各版の符号化・ドメイン）は従来どおりである。
- **集計は旧版を常に対象外とする**: 旧版バンドルの提出は帰属なしで却下し、理由（現行版でないこと）を記録する。失格にはしない（§10）。
- v0.3 バンドルの生成・検証には §4 のパラメータ表（プロファイル）が必須であり、プロファイルは検証者の文脈で決まる。`test` プロファイルはテスト専用で、本番検証では使わない。

## 13. アプリ側実装への要求（コンパニオン等の参加アプリ）

本仕様の検証・集計が正しくても、参加アプリ側の実装が緩ければ証明は崩れる。v0.3 レビューでアプリ側に見つかった問題（H-04、M-01、M-02、M-04、L-01）は、仕様の問題ではなく実装の問題だが、再発防止のため要求として明記する。**これらは参照実装（Python）の範囲外であり、アプリ側の担当が満たすこと**:

- **ジャーナルの完全性・認証（H-04）**: アプリが観測を蓄積するジャーナルは、書き換えを検出できる形（例: 各記録への連鎖ハッシュ＋ID鍵による署名、または同等の認証）で保存すること。無認証の平文ジャーナルを読み込んで、その内容に ID 鍵で署名して書き出す構造は、端末内の書き換えにアプリ自身が「正規の署名」を与えてしまうため禁止する。
- **ジャーナルの部分書込みからの復旧（v0.5、R-M04）**: 追記型ジャーナル（JSONL 等）は、書き込み途中の終了で末尾行が不完全になり得る。ジャーナルを開く際は、**追記を始める前に不完全な末尾行を切り捨てる**こと（ライブジャーナルと移行アーカイブの両方に適用）。切り捨てずに追記すると、不完全な行と次の記録が連結した壊れた行が生まれ、その行と後続全体が次回読み込みで破棄される。検証で落ちた地点より後ろを破棄する規則自体は維持してよいが、「正常な記録が巻き添えで増えていく」形にしてはならない。
- **ジャーナルヘッダの復旧（v0.6、B4-F1／F2）**: ジャーナルのヘッダ行（identity 等を記した先頭行）は、それ自体には署名等の完全性保護がない。敵対テストで、ヘッダの欠落・読解不能では読み込みが例外を投げて履歴全体を開けなくなり、ヘッダ内の identity 損傷では自分のジャーナルが「他人のもの」として弾かれる単一障害点が見つかった。したがって: (1) **ジャーナルの読み込みは、ファイル内容を理由とする例外をストアの外へ漏らしてはならない**。(2) ヘッダが欠落・読解不能な場合、またはヘッダの identity が期待する identity（鍵保管庫側の identity）と異なる場合は、そのファイルを**バイト列を保ったまま隔離（quarantine）**し（別名で退避し、黙って削除しない）、鍵保管庫の identity に束縛した新しいジャーナルを開始すること。復旧が発生したことは利用者に分かる形で表面化させること。(3) 記録本体の受け入れは従来どおり署名・連鎖の検証で決める（ヘッダの状態は記録の真正性の根拠にしない）。「壊れた自分のヘッダ」と「他人のジャーナル」を、例外で落とすことで区別する設計にしてはならない。
- **移行時署名の例外と由来表示（v0.5、再監査の SPEC 不一致指摘を受けて明記）**: 旧形式ジャーナルの移行（コンパニオン v0.2.1 の `migrateLegacy`）で移行先アーカイブの記録に付ける署名は、**「移行時点の保存内容がその後改ざんされていないこと」の認証であり、過去の観測自体の真正性の証明ではない**。この例外は本節の「無認証履歴への署名禁止」の例外として位置づけ、アーカイブ側には移行由来であることを区別できる形で残し、ライブの履歴と混ぜないこと。
- **RPC 応答の妥当性検証（M-02。v0.5 で R-M02／R-M03 を受けて具体化）**: ローカル RPC の応答は無条件に信用しない。具体的な要求は次のとおり:
  - **数値の厳密な正規パース**: ブロック番号等の16進数量は `0x` の後に16進数字のみが続く形だけを受け付ける。符号（`"0x-1"` 等）、空白、その他の文字を含む値は解析時点で拒否する（負数が「正規の観測」として署名・保存されることがあってはならない）。値の上限は i64 の最大値以下とし、さらに `best`／`finalized` には絶対上限（2^48 未満）を設ける。
  - **保存前の整合性検査**: `finalized <= best` 等を保存前に検査し、汚染された観測は記録せずに切り分けること。
  - **実効する全体期限**: 観測ラウンド全体の期限（現行 20 秒）は、接続・読み取りのタイムアウトで実際に強制すること。本文の読み取り中も期限が効き、ピアID取得の呼び出しも期限の対象に含める（チェックを通信の前後に置くだけでは、応答しない接続先が観測スレッドを占有し続ける）。
  - **初回観測と後退の自己回復**: 初回観測にも絶対上限などの妥当性検査を適用する（「初回だから無検査」で巨大値を基準に取り込むと、その後の正規値が恒久的に「後退」と判定され観測が止まる）。正規ノードの再起動・再編成等で値が後退し続ける場合は、**3回連続の後退で新しい基準として採用し直す**自己回復を行い、恒常的な観測停止にしないこと。
  - 接続先が正規のノードであることの認証は現状の RPC では得られないため、その限界（同一端末内の別アプリが先にポートを確保すれば偽観測を取り込み得る）はアプリの文書に明記すること。
- **検証条件のパリティ（M-01）**: アプリ側の検証・生成は参照実装と完全に一致させること。特に、整数の正規化（`8.0` を `8` とみなす等）の禁止、16進正規形（小文字）の強制、厳密なスキーマ検査（必須・未知項目、件数、範囲）、witness 配列の保持と符号化。参照実装と判定が分かれる入力は、それ自体が不具合である。
- **長期蓄積の設計（M-04）**: ジャーナルは全履歴の再書きを避ける追記型の設計とし、構築・署名・自己検証は UI スレッドで行わないこと。参照実装のチェックポイント数上限（200,000）を超える履歴を1バンドルに詰め込まないこと。**現時点の到達点と残課題を正直に区別する**: 追記型ジャーナル・裏スレッドでの書き出し・上限の明示までは実装済みの到達点であり、**期間単位の分割書き出しは将来課題として未実装**である。分割が未実装の間、上限（現行 100,000 件）を超える書き出しは、**黙って切り捨てた不完全なバンドルを出すのではなく、拒否してその旨を利用者に通知する**こと（先頭を切り出したバンドルは単独では検証できないため、切り捨ては「出せたように見える壊れた出力」になる）。
- **秘密鍵の保持期間（L-01。v0.5 で R-L01 を受けて具体化）**: seed の平文をメモリに保持するのは署名に必要な最小の期間・範囲に限り、不要になったら破棄（ゼロ化）すること。**平文 seed のキャッシュは持たない**: 必要な都度、保管庫から復号して使い、使い終わったらゼロ化する。公開鍵の取得だけのために seed を保持し続けないこと（公開鍵は導出後に公開鍵だけを保持すれば足りる）。`publicKey()` のように内部で seed を取り出す経路でも、取り出した複製は呼び出し側・内部の両方でゼロ化すること。
